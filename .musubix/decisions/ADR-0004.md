# ADR-0004: プロジェクトファイル形式と永続化方式の選定

## Context / 背景
REQ-POTTERY-015は、スキャンデータへの参照＋内容確認用ハッシュ、推定結果、手動編集
内容を1つのプロジェクト状態として保存・再読込できることを要求する。REQ-POTTERY-023
は保存処理の原子性（失敗時に既存ファイルを破損させないこと）、REQ-POTTERY-024は
読込時の参照先スキャンデータ欠落・変更の検出を要求する。

## Decision / 決定
プロジェクトファイルは、JSONマニフェスト（スキーマバージョン、破片スキャンファイル
への参照パスとSHA-256ハッシュ一覧）と、推定結果・手動編集内容を格納するJSON文書群を
1つのZIPコンテナ（拡張子 `.kintsugiproj`）にまとめて保存する。生スキャンデータ本体は
コンテナに埋め込まず、外部ファイルへの参照とハッシュのみを保持する。保存処理は
一時ファイルへ書き込み完了後にアトミックなリネームで既存ファイルを置き換える方式
（write-temp-then-rename）とする。

## Rejected Alternatives / 却下した代替案
- **単一の独自バイナリ形式**: デバッグ・検査が困難であり、部分的な破損時の復旧や
  将来のスキーマ拡張時の後方互換対応コストが高い。
- **生スキャンデータをプロジェクトファイルに埋め込む方式**: 破片100点規模の点群・
  テクスチャデータを埋め込むとファイルサイズが著しく肥大化し、既に外部管理されて
  いるスキャンデータと重複保持することになり、REQ-POTTERY-015の「参照＋ハッシュ」
  という要求そのものと矛盾する。
- **直接上書き保存（一時ファイルを介さない）**: 保存途中でのプロセス異常終了時に
  既存プロジェクトファイルを破損させる可能性があり、REQ-POTTERY-023の原子性要求を
  満たせない。

## Consequences / 結果
write-temp-then-rename方式により保存失敗時も直前の保存済みファイルが保持される。
読込時はマニフェスト中のハッシュと実ファイルのハッシュを比較し、不一致・欠落を
破片単位で検出・報告する（REQ-POTTERY-024）。ZIPコンテナ形式のため将来的な圧縮・
部分検査ツールとの親和性も確保される。
